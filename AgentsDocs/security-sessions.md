# Устройства, сеансы и журнал безопасности

Документ описывает учёт входов в DevHome.Identity: какие данные сохраняются, как
работают политики, что делают кнопки отзыва и блокировки, где смотреть журнал.

Код вынесен в библиотеку `Common.Security.OpenIddict.Server`; клиентская часть
OpenID Connect — в `Common.Security.OpenIddict.Client`. Подробности подключения —
в `README.md` этих проектов.

## 1. Что сохраняется

При каждом успешном входе создаётся запись `UserSession`:

| Поле | Откуда берётся |
|---|---|
| `UserId` | Identity |
| `DeviceId` | постоянная cookie устройства |
| `ClientId` | приложение, из которого начат вход |
| `ApplicationName` | название приложения из OpenIddict |
| `CreatedAt`, `LastSeenAt` | время создания и последней активности |
| `ExpiresAt` | срок сеанса (по умолчанию 30 дней) |
| `IpAddress` | `RemoteIpAddress` или доверенный `X-Forwarded-For` |
| `Location` | заголовки прокси или подпись «локальная сеть» / «этот компьютер» |
| `UserAgent` | строка браузера |

Устройство `UserDevice` хранит:

- `DisplayName` — например, `Chrome 131 · Windows 11`;
- `Browser`, `OperatingSystem`, `DeviceType`;
- первый и последний IP, последнюю локацию, user agent;
- `IsBlocked`, `BlockedAt`, `BlockedBy`, `BlockReason`.

В `UserSessionApplication` сохраняются приложения, в которые входили в рамках сеанса,
и запрошенные области. Один сеанс Identity может использоваться несколькими
приложениями: DevHome, MAUI, WPF, CLI.

`UserLoginAudit` — журнал событий: `SignIn`, `ApplicationAuthorized`, `SessionRevoked`,
`AllSessionsRevoked`, `DeviceBlocked`, `DeviceUnblocked`, `PolicyChanged`,
`SignInRejected`. В подробностях входа сохраняется способ (`amr`): пароль, второй фактор,
ключ доступа или внешний провайдер. Журнал не удаляется при отзыве сеанса.

## 2. Как определяется устройство

При первом входе создаётся случайное значение, кладётся в cookie `DevHome.Device`
и сохраняется в базе как SHA-256-хеш. Cookie:

- `HttpOnly`;
- `SameSite=Lax`;
- `Secure` при HTTPS;
- срок — два года.

Пока cookie сохраняется, один и тот же браузер на одном компьютере считается одним
устройством. Очистка cookie или другой браузер создают новое устройство. Это не
ошибка: без cookie отличить «тот же браузер» от нового невозможно.

Если пользователь заходит в режиме инкогнито, появится отдельное устройство.
Если он очистил cookie, старые сеансы останутся в истории, но новое устройство
будет считаться новым.

## 3. Политики входа

Пользователь выбирает политику в разделе **Аккаунт → Устройства и сеансы**.
Администратор может изменить её в карточке пользователя.

| Политика | Что происходит |
|---|---|
| **Несколько устройств** | вход разрешён с любого числа устройств |
| **Одно устройство: новый вход побеждает** | новый вход автоматически завершает все предыдущие сеансы |
| **Одно устройство: сначала завершите старый сеанс** | новый вход отклоняется, пока пользователь или администратор не завершит старый сеанс |

Третья политика — самая строгая. Если старое устройство потеряно, пользователь
не сможет войти, пока администратор не завершит его сеанс в админке. Об этом
написано в подсказке на странице.

При смене политики на «одно устройство» самый свежий сеанс остаётся, остальные
завершаются сразу, чтобы политика действовала не только со следующего входа.

## 4. Отзыв и блокировка

### Завершить сеанс

Пользователь: **Устройства и сеансы → Завершить**.
Администратор: **Пользователи → карточка → Устройства и сеансы → Завершить** или
**Сеансы и устройства → Завершить**.

Что происходит:

1. сеанс помечается `RevokedAt`, `RevokedBy`, `RevokeReason`;
2. связанные приложения помечаются отозванными;
3. токены OpenIddict для приложений сеанса отзываются;
4. cookie Identity перестаёт приниматься на следующем запросе;
5. API при следующей проверке токена получает `active: false`.

Если завершается текущий сеанс, пользователь сразу выходит из личного кабинета.

### Заблокировать устройство

Пользователь или администратор нажимает **Заблокировать**.

Что происходит:

1. `UserDevice.IsBlocked = true`;
2. все сеансы этого устройства завершаются;
3. токены этих сеансов отзываются;
4. будущие входы с этого устройства отклоняются на странице входа.

Разблокировка снимает запрет, но **не восстанавливает** старые сеансы. Для входа
нужно снова ввести пароль (и второй фактор, если он включён).

### Завершить все сеансы

Кнопка **Завершить все сеансы и отозвать токены** в карточке пользователя:

- завершает все сеансы;
- отзывает все токены и авторизации OpenIddict пользователя;
- обновляет security stamp, чтобы cookie Identity перестали действовать.

Это действие удобно при подозрении на компрометацию учётной записи.

## 5. Где смотреть

| Страница | Кто видит | Что показывает |
|---|---|---|
| `/Account/Manage/Sessions` | пользователь | свои сеансы, устройства, политику, журнал |
| `/admin/sessions` | администратор | все активные сеансы и последние события |
| `/admin/users/{id}` | администратор | карточка пользователя, его сеансы и устройства |
| `/admin` | администратор | счётчик активных сеансов |

Журнал хранится `Security:Sessions:AuditRetention` дней (по умолчанию 180).
В DevHome.Identity очистку раз в сутки выполняет `SecurityCleanupService`; в другом
приложении вызовите `IUserSecurityService.CleanupAuditAsync` по расписанию.

## 6. Приватность и ограничения

- IP-адрес берётся из подключения. `X-Forwarded-For` по умолчанию не используется:
  его легко подделать. Включайте `Security:Sessions:TrustForwardedHeaders=true` только
  за известным reverse proxy.
- Геолокация по IP не выполняется: библиотека не отправляет адреса во внешние сервисы.
  Локация берётся из заголовков доверенного прокси или подписывается как «локальная сеть».
- Отзыв сеанса не делает принудительный back-channel logout клиентского приложения.
  Приложение узнает об отзыве при следующем обращении к API или при проверке сеанса.
- Для нескольких экземпляров Identity нужны общая база и общие ключи Data Protection.
- В локальной сети включён HTTP. Для выхода в интернет обязателен HTTPS.

## 7. Диагностика

При первом запуске новой версии старые cookie Identity не содержат `sid`, поэтому
будут отклонены: пользователи один раз войдут заново. Это ожидаемое обновление схемы,
а не ошибка. После входа cookie создаётся заново с `sid`.

| Симптом | Что проверить |
|---|---|
| После входа сразу выбрасывает на страницу входа | В cookie нет `sid` или сеанс отозван. Проверьте `Security_UserSessions` и журнал. |
| Пользователь не может войти после смены политики | Включена политика «сначала завершите старый сеанс», есть активный сеанс на другом устройстве. Завершите его в админке. |
| Новое устройство появляется при каждом входе | Браузер не сохраняет cookie `DevHome.Device` (приватный режим, очистка, блокировка cookie). |
| API отвечает 401 после отзыва | Это ожидаемо: токены отозваны. Нужен новый вход. |
| В журнале нет событий | Проверьте, что миграция `AddDeviceSecurity` применена и `Database:AutoMigrate` не отключён. |
