# Администрирование и личный кабинет DevHome.Identity

Описание админ-панели Identity и переработанного личного кабинета: маршруты, права,
возможности и принятые решения. Код: `DevHome.Identity/Components/Admin/*`,
`DevHome.Identity/Components/Account/*`, `DevHome.Identity/Administration/*`.
Настройки OpenIddict: [openiddict-reference.md](openiddict-reference.md).

## 1. Роли и доступ

| Роль | Назначение |
|---|---|
| `Admin` | Полный доступ к страницам `/admin`: пользователи, клиенты, области, токены. |
| `User` | Обычный пользователь: личный кабинет и страницы приложения. |

Роли создаются при первом запуске (`OpenIddictSeeder.EnsureRolesAsync`). Администратор
назначается по адресу из `Identity:Admin:Email`; в Development, если ключ пуст,
администратором становится демо-пользователь `demo@devhome.local`.

```json
"Identity": {
  "Admin": {
    "Email": "admin@example.com"
  }
}
```

Страницы админки помечены `[Authorize(Roles = AdminRoles.Administrator)]`, пункты меню —
`Roles = AdminRoles.Administrator`. Пользователь без роли не видит раздел
«Администрирование» в боковом меню, а при прямом переходе попадает на
`/Account/AccessDenied` с пояснением.

Вход принимает адрес электронной почты: `Login.razor` сначала ищет пользователя по имени,
затем по почте. Это позволяет администратору задать отдельное имя пользователя, не ломая
вход по почте.

## 2. Страницы администрирования

| Маршрут | Что делает |
|---|---|
| `/admin` | Сводка: пользователи, клиенты, области, действующие токены, последние авторизации, издатель и адреса конечных точек. |
| `/admin/users` | Список пользователей: поиск по почте/имени/телефону, фильтр по роли, постраничный вывод. |
| `/admin/users/new` | Создание пользователя: почта, имя, пароль, телефон, подтверждение почты, роли. |
| `/admin/users/{id}` | Карточка пользователя: основные сведения, роли, пароль, блокировка, подтверждение почты, сброс 2FA, завершение сеансов, ключи доступа, внешние входы, удаление. |
| `/admin/clients` | Клиентские приложения OpenIddict: тип, согласие, адреса возврата, сценарии, области, PKCE. |
| `/admin/clients/new` | Создание клиента: Client ID, название, тип, согласие, секрет, адреса, разрешения. |
| `/admin/clients/{id}` | Редактирование клиента: смена названия и Client ID, секрет (задать/удалить), адреса, разрешения и требования, удаление с отзывом токенов. |
| `/admin/scopes` | Список областей и форма создания. |
| `/admin/scopes/{id}` | Редактирование области: название, описание, ресурсы; удаление. |
| `/admin/tokens` | Авторизации и токены: фильтры, вкладки, отзыв, удаление, очистка просроченных. |

### 2.1. Пользователи

- Пароль задаётся администратором через `GeneratePasswordResetTokenAsync` + `ResetPasswordAsync`
  (старый пароль не нужен), после чего все сеансы пользователя завершаются.
- Блокировка выставляет `LockoutEnd` на 100 лет; разблокировка снимает срок и сбрасывает
  счётчик неудачных попыток.
- «Завершить все сеансы» обновляет `SecurityStamp` и отзывает токены и авторизации
  (`RevokeBySubjectAsync`) — пользователь выходит из всех клиентов.
- Удаление запрещено для собственной учётной записи и для единственного администратора.
  Токены и авторизации удаляемого пользователя предварительно отзываются.
- Ключи доступа можно удалить из карточки; внешние входы показаны для справки.

### 2.2. Клиенты OpenIddict

- Секрет никогда не показывается. Пустое поле — «не менять», заполненное — заменить,
  флажок «Удалить текущий секрет» — снять. При смене типа на «публичный» секрет
  удаляется автоматически.
- Разрешения редактируются флажками по группам: конечные точки, сценарии, типы ответа,
  области, требования. Значения берутся из констант OpenIddict
  (`Administration/OpenIddictPermissionCatalog.cs`), поэтому подписи не расходятся с API.
- Адреса возврата вводятся по одному в строке и проверяются как абсолютные URI.
- Удаление клиента сначала отзывает его токены и авторизации, затем удаляет запись.

### 2.3. Токены и авторизации

Данные читаются напрямую из `OpenIddictAuthorizations`/`OpenIddictTokens` через
`IDbContextFactory<DBContext>` (фильтры, сортировка и страницы — в SQL, без N+1).
Области авторизации хранятся JSON-массивом и разбираются
`Administration/OpenIddictValueParser.cs`. Действия: «Отозвать», «Удалить»,
«Удалить просроченные» (`PruneAsync`). Типы токенов показываются по-русски
(access, refresh, identity, код авторизации, код устройства, код пользователя).

## 3. Личный кабинет

Вместо семи пунктов шаблона — три страницы:

| Маршрут | Содержимое |
|---|---|
| `/Account/Manage` | Профиль: имя пользователя, телефон, почта с подтверждением и сменой, роли, сводка состояния. |
| `/Account/Manage/Security` | Пароль (задать или изменить), двухфакторная аутентификация, ключи доступа, внешние входы. |
| `/Account/Manage/PersonalData` | Скачивание данных в JSON и удаление учётной записи с подтверждением паролем. |

Объединённые страницы сохранили старые адреса и перенаправляют на новые:

| Старый адрес | Куда ведёт |
|---|---|
| `/Account/Manage/Email` | `/Account/Manage` |
| `/Account/Manage/ChangePassword` | `/Account/Manage/Security` |
| `/Account/Manage/SetPassword` | `/Account/Manage/Security` |
| `/Account/Manage/TwoFactorAuthentication` | `/Account/Manage/Security` |
| `/Account/Manage/Passkeys` | `/Account/Manage/Security` |
| `/Account/Manage/DeletePersonalData` | `/Account/Manage/PersonalData` |

Многошаговые сценарии остаются отдельными: `EnableAuthenticator`,
`GenerateRecoveryCodes`, `Disable2fa`, `ResetAuthenticator`, `RenamePasskey`,
`ExternalLogins`.

Пока почта не настроена (SMTP нет), письма не уходят. На странице профиля в Development
показывается готовая ссылка подтверждения — это позволяет проверять смену почты без
почтового сервера.

## 4. Пункты меню

Страницы сами описывают себя атрибутом `[MenuItem]`, поэтому меню не собирается вручную:

- раздел «Аккаунт»: «Личный кабинет», «Безопасность», «Личные данные» — только вошедшим;
- раздел «Администрирование»: «Обзор», «Пользователи», «Клиенты», «Области», «Токены» —
  только роли `Admin`.

Служебные страницы (`/admin/users/new`, `/admin/users/{id}` и т. п.) помечены
`Hidden = true`: маршрут работает, но в меню не попадает.

## 5. Устройство страниц

| Решение | Причина |
|---|---|
| Админка — `InteractiveServer` | Поиск, фильтры, подтверждения и CRUD без полной перезагрузки; формы и антифоржерия обрабатывает Blazor. |
| Личный кабинет — статический SSR | Как в шаблоне Identity: работа с `HttpContext`, cookie и формами (`[SupplyParameterFromForm]`) без схемы Blazor. |
| `IDbContextFactory<DBContext>` в админке | Отдельный контекст на запрос вместо долгоживущего контекста схемы; нет конфликтов при параллельной загрузке. |
| Данные пользователя в меню кабинета — из cookie | Меню и страница инициализируются параллельно; обращение к `UserManager` из меню создавало бы второй запрос на том же `DbContext`. |
| `GlobalUsings.cs` | Пространство `DevHome.Identity.OpenIddict` перекрывает корневое `OpenIddict`, поэтому типы пакета подключены через `global using`. |
| Только Bootstrap | Новые компоненты библиотеки не понадобились; админка собрана из карточек, таблиц, вкладок, значков и форм Bootstrap 5. |

## 6. Проверка

- `dotnet build PersonalKit.slnx` — без предупреждений и ошибок.
- `dotnet run --project Testing` — все тесты проходят.
- Проверено в браузере (Chrome, CDP):
  - создание, блокировка, смена пароля и удаление пользователя;
  - создание, сохранение без смены секрета и удаление клиента;
  - создание, изменение и удаление области;
  - вкладки и фильтры авторизаций и токенов;
  - вход пользователя без роли `Admin`: раздел меню скрыт, прямой переход даёт отказ;
  - профиль: сохранение и очистка телефона, ссылка смены почты;
  - скачивание личных данных (`200`, `application/json`);
  - мобильная ширина 390 px: боковая панель скрыта, открывается кнопкой, горизонтальной
    прокрутки нет.

## 7. Ограничения

- Админка не ведёт журнал действий: изменения видны в логах приложения, но отдельной
  истории в базе нет.
- SMTP не подключён: подтверждение почты и сброс пароля показывают ссылку только
  в Development.
- В Development клиент `devhome-web` пересоздаётся при каждом запуске (так применяются
  изменения адресов возврата). Его секрет при этом пересчитывается — это нормально.
- Ключи подписи в Development хранятся в памяти: после перезапуска ранее выданные
  токены недействительны.
